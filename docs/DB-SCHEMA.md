# DwellyProperty — Database & Security Model (MySQL 8)

- **Schema (source of truth):** `web/src/server/db/schema.ts` (Drizzle ORM)
- **Migrations:** `web/drizzle/` (generated by `npm run db:generate`)
- **Business rules / permissions:** `web/src/server/services/*`
- **Tests:** `web/tests/services.test.ts` (runs on a real throwaway MySQL)

## หลักการออกแบบ

1. **การคุมสิทธิ์อยู่ใน service layer:** MySQL ไม่มี Row-Level Security ทุกการอ่านและเขียนจึงต้องผ่านฟังก์ชันใน `src/server/services/*` ซึ่งตรวจสิทธิ์ทุกครั้ง ได้แก่ เจ้าของข้อมูล บทบาท staff สถานะบัญชี และลำดับสถานะ (state machine) **หน้าเว็บและ server action ห้ามเขียนตารางเองโดยตรง**
2. **ทุกแถวอ้างถึงผู้ใช้ด้วย id:** ประกาศมี `owner_id`/`agent_id` และดีลมี `buyer_id`/`seller_id`
3. **ฟิลด์ที่ผู้ใช้ห้ามแก้:** service ไม่รับ `is_verified`, `status`, ตัวนับ, `featured_until` และ `listed_price` จาก input ของผู้ใช้เลย
4. **การตัดสินใจของ staff:** เปลี่ยนข้อมูลภายใน transaction เดียวกับการบันทึก `audit_logs` และ `notifications`
5. **ข้อมูลติดต่อ (PDPA):** `profiles.phone`/`line_id` ไม่ถูก select ใน query สาธารณะ ผู้อื่นเห็นได้ผ่าน `revealContact()` เท่านั้น ซึ่งต้องล็อกอินและบันทึก event ทุกครั้ง
6. **เวลา:** เก็บเป็น `DATETIME(3)` แบบ UTC และแอปได้รับเป็น ISO string
7. **ID:** ใช้ UUID (`varchar(36)`) ส่วนรหัสที่คนอ่าน (DW001234, AG1001, POD-101) สร้างจากตาราง `counters` ภายใน transaction

## State machines (บังคับใน service)

- **ประกาศ** (`listings.changeListingStatus`, `reviewListing`)
  - เจ้าของเปลี่ยนได้: draft/rejected → pending_review, pending_review → draft, active ⇄ reserved, active/reserved → sold/rented, expired/sold/rented/archived → pending_review (ส่งตรวจใหม่), และปิดประกาศ (archived) ได้ทุกเมื่อ
  - **เจ้าของตั้งเป็น active เองไม่ได้:** ต้องผ่าน moderator และต้องมีรูปอย่างน้อย 1 รูปก่อนส่งตรวจ
- **ข้อเสนอ**
  - ผู้ขาย: pending → accepted/rejected/countered
  - ผู้ซื้อ: countered → accepted/rejected และถอน (withdrawn) ได้ระหว่าง pending หรือ countered
  - ข้อเสนอที่หมดอายุแล้วแก้ไขไม่ได้
- **นัดหมาย**
  - ผู้ขาย: pending → confirmed/declined, confirmed → completed/no_show
  - ทั้งสองฝ่ายยกเลิกได้
  - ต้องนัดล่วงหน้าอย่างน้อย 1 ชั่วโมงและไม่เกิน 90 วัน
- **การยืนยันเอกสาร**
  - pending → approved/rejected/needs_info
  - needs_info → pending เมื่อผู้ใช้ส่งข้อมูลเพิ่ม
  - เมื่ออนุมัติจะตั้ง badge ให้อัตโนมัติ

## บทบาท Staff

| role | สิทธิ์ |
|---|---|
| `super_admin` | ทุกอย่าง และจัดการทีมงาน |
| `moderator` | ตรวจ/ระงับ/แนะนำประกาศ, Hubs/Zones, รายงานปัญหา, Co-Agent partner |
| `verifier` | KYC, โฉนด, ใบอนุญาตนายหน้า, Pods (เปิดดูไฟล์เอกสารได้) |
| `support` | ผู้ใช้ (ระงับ/แบน), รายงานปัญหา, คำขอลบบัญชี |
| `finance` | แพ็กเกจ, คำสั่งซื้อ (ยังไม่มีหน้า UI) |

## ไฟล์ที่อัปโหลด

ไฟล์เก็บบนดิสก์ของเครื่อง host ที่ `STORAGE_DIR` ตาม path `{bucket}/{userId}/{scope}/{uuid}.{ext}` อัปโหลดผ่าน `POST /api/upload` และเปิดผ่าน `GET /files/{bucket}/...`

| bucket | ใครเปิดได้ |
|---|---|
| `avatars`, `property-media` | ทุกคน (cache 1 ปี) |
| `verification-docs` | เจ้าของไฟล์ + verifier |
| `chat-attachments` | สมาชิกในห้องแชท + support |

## งานตามเวลา

`npm run maintenance` หรือ `POST /api/cron/maintenance` (ส่ง header `Authorization: Bearer $CRON_SECRET`) ให้รันทุกชั่วโมง งานที่ทำ:
- เตือนเจ้าของประกาศก่อนหมดอายุ 3 วัน
- ปรับประกาศที่ครบกำหนดเป็นหมดอายุ (expired)
- ปรับข้อเสนอที่หมดเวลาเป็นหมดอายุ
- ปิด subscription ที่หมดอายุ
- เปลี่ยนสถานะ Hubs ตามวันเวลา (scheduled → live → ended)

## Realtime

แชทใช้ Server-Sent Events (`GET /api/chat/{id}/stream`) ผ่าน event bus ภายในโปรเซส Node ซึ่งใช้ได้เมื่อรันแอป **โปรเซสเดียว** ถ้าจะขยายเป็นหลาย instance ต้องเปลี่ยนไปใช้ Redis pub/sub
